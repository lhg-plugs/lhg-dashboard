# lhg-db-audit：看板审计方法论

> 目标：用"机器查规范 + 人查诚实"的两层筛子，保证交付的每块看板都不误导人。
> 核心纪律：**blocker 清零才能说"看板做好了"；为清零改规则是作弊。**

## 1. 何时使用

- 看板规格写完准备交付前 → 必须跑本 skill
- 接手别人做的看板想快速找毛病 → 跑本 skill 第 3-5 步
- 给老板汇报前终审 → 跑全量（含第 5 步人工评审）
- 只想出规格不想自查 → 不许跳过本 skill，这是插件的硬门

## 2. 输入与输出

- **输入**：看板规格 Markdown（按本插件章节结构写）+ 指标体系表（可选）
- **输出**：自查报告，含：脚本发现（blocker / warning / nit 明细）+
  人工评审结论（通过 / 不通过）+ 需人工处理项清单

## 3. 第一步：跑确定性审计脚本

```bash
python3 <插件目录>/scripts/audit/dashboard_audit.py --target <规格目录> --format text
```

脚本零第三方依赖，规则分五大类：

| 类别 | 查什么 | 典型 blocker |
|---|---|---|
| 图表选型（CHART） | 饼图分类数、折线是否时序、双轴/3D | 饼图分类 >6 |
| 色板（COLOR） | 红绿搭配、颜色数是否够分 | —（warning） |
| 指标（METRIC） | 单位、时间范围、口径定义三件套 | 指标缺单位/时间范围 |
| 布局（LAYOUT） | 一屏图表数、图表标题 | —（warning） |
| 刻度（SCALE） | 柱状图 Y 轴是否截断 | —（warning） |

分级定义：

- **blocker**：必须修，不修不许交付；commit 前 hook 会拦截。
- **warning**：修掉，或写豁免理由（为什么这次可以例外）。
- **nit**：顺手修，不修也要在报告里列出来。

## 4. 第二步：分级处置

1. blocker 逐条修：修一条用脚本复查一条，确认清零。
2. 修不掉的 blocker（如需要用户确认真实口径、数据源字段）→
   列入"需人工处理"，**不许**为清零改脚本规则或阈值。
3. warning 修掉或写豁免理由；nit 顺手修。
4. 全部处理完再跑一遍脚本，确认 blocker 为 0。

## 5. 第三步：人工评审清单（脚本抓不到的）

脚本只查结构与显式声明，以下一律人工过：

### 5.1 指标可行动性

- 每个指标变了，有人知道该干什么吗？没人行动的指标是装饰，删。
- 北极星指标真的是 1 个吗？3 个北极星等于没有北极星。

### 5.2 图表诚实性

- 有没有用截断 Y 轴、双轴、3D 夸大/缩小差异？（脚本只查"说明"里自曝的，藏着掖着的要人看）
- 饼图的"其他"项占比超过 50% 吗？超过说明 TopN 没抓住重点。
- 折线图的 X 轴时间间隔均匀吗？（不等距的时间轴会扭曲斜率）

### 5.3 标题诚实性

- 标题说的是图里实际画的东西吗？（标题写"趋势"，图里却是分类对比 → 不通过）
- 时间范围写对了吗？（图是 10 月上旬，标题写"10 月"→ 打回）

### 5.4 色板现实性

- 在投影仪上还分得清吗？在手机小屏上还分得清吗？
- 黑白打印还能区分吗？不能 → 加数据标签或纹理。

### 5.5 数据诚实性

- 规格里引用的数据源字段是真实存在的吗？编造的 → 标 blocker 打回。
- 有"数据截至 XXXX"字样吗？没有时效性的看板等于过期食品。
- 口径定义里的边界（是否含退款、是否含税）用户确认过吗？

## 6. 第四步：输出自查报告（模板）

```markdown
# 看板自查报告（<看板名称>，<日期>）

## 脚本审计
- blocker：N（已清零 / 剩余 M，见下）
- warning：N（已修复 N1，豁免 N2）
- nit：N

## 人工评审
- 指标可行动性：通过 / 不通过（理由）
- 图表诚实性：通过 / 不通过（理由）
- 标题诚实性：通过 / 不通过（理由）
- 色板现实性：通过 / 不通过（理由）
- 数据诚实性：通过 / 不通过（理由）

## 结论：通过 / 不通过

## 需人工处理项
1. ……
```

结论只能是"通过"或"不通过"，不许写"基本通过""大致没问题"。

## 7. 审计脚本规则速查表（完整版）

| 规则 ID | 级别 | 查什么 | 触发条件 |
|---|---|---|---|
| DB-CHART-001 | blocker | 饼图分类过多 | 饼图/环形图分类 >6 |
| DB-CHART-002 | warning | 折线图用于非时序 | 折线图数据维度无时序词 |
| DB-CHART-003 | warning | 双轴误导风险 | 图表类型含"双轴" |
| DB-CHART-004 | warning | 3D 误导风险 | 图表类型含 3D/三维 |
| DB-COLOR-001 | warning | 色盲不友好 | 色板同时含红/绿色系 |
| DB-COLOR-002 | warning | 颜色不够分 | 色板颜色数 < 最多分类数 |
| DB-METRIC-001 | blocker | 指标缺单位 | 单位列为空 |
| DB-METRIC-002 | blocker | 指标缺时间范围 | 时间范围列为空 |
| DB-METRIC-003 | warning | 口径未定义 | 口径定义 <10 字 |
| DB-LAYOUT-001 | warning | 一屏图表过多 | 一屏图表数 >8 |
| DB-LAYOUT-002 | warning | 图表缺标题 | 标题列为空 |
| DB-SCALE-001 | warning | Y 轴截断 | 柱状图说明含截断表述 |

规则阈值（6 分类、8 张图、10 字口径）是经验值，
如需调整必须在自查报告里写理由，**不许静默改脚本**。

## 8. 反模式（不要这么做）

- ❌ 脚本报 blocker，手动改脚本阈值让它变绿——这是作弊，不是修复
- ❌ warning 全写"豁免：时间紧"——豁免要有真理由，"时间紧"不算
- ❌ 人工评审只看一遍就说"挺好的"——按 5.1-5.5 逐项过，逐项写结论
- ❌ 报告结论写"基本通过"——只有通过/不通过两种结论
- ❌ 发现编造的数据源字段，只改成"需核实"就放行——这是 blocker，必须让用户确认后重写

## 9. 自检与反馈

每次执行完本 skill，做一次轻量自检（不额外输出打扰用户）：

1. 脚本跑了吗？blocker 真清零了吗？→ 没跑就说"通过"是不许的。
2. warning 都有处置（修复/豁免）吗？→ 裸奔的 warning 下次会变成 blocker。
3. 人工评审 5 项都写了结论吗？→ 缺项补上。
4. 需人工处理项列清楚了吗？→ 不要让用户猜。

如发现本 skill 自身的方法论缺陷，按以下流程反馈：

- **标准冒烟用例**：拿 fixtures/dashboard-bad/spec.md 跑一遍，
  检查 12 条规则埋点是否全命中、人工评审能否发现"标题与图不符"这类问题。
- **一键提 issue**：确认问题后，以 `[QC] <一句话问题>` 为标题、
  正文写清"复现输入 → 错误输出 → 期望输出"，
  提交到 https://github.com/lhg-plugs/lhg-dashboard/issues。
